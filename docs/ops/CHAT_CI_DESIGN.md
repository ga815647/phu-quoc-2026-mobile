# Chat 修改與 CI 驗站：已確認方向與待定契約

日期：2026-09-27。使用者已確認採用「Chat 修改 Neon → CI 驗正式站 → GitHub 回報」方向。
此文件是設計輸入，不代表新 workflow、公開版本或六天資料模型已實作；寫碼前仍需規格與計畫審閱。

## 已確認的責任

1. Chat 從 GitHub 固定 commit 讀規則、從 Neon 讀寫最新授權內容並讀回／核對稽核。
2. Chat 用已驗證的建分支／寫 JSON 能力提出驗站請求，不依賴不存在的 workflow_dispatch 工具。
3. CI 使用瀏覽器檢查正式站當次修改及手機呈現；不替 Chat 改 Neon，不將驗站與部署綁成一個操作。
4. JSON／文字報告放專用結果分支，讓 Chat 以 GitHub 原檔工具讀回；截圖等另外存 Actions artifact。
5. Chat 分別回報「資料已儲存」與「網站已驗證」，第二項未通過時不能混稱完成。

## 現有基礎與缺口

- `data-smoke.yml` 已有 Chromium／手機尺寸正式 Pages 測試；目前只在 main 的指定路徑 push 或手動 dispatch 觸發，主要輸出 log，未提供本次資料修改的版本回報。
- Chat 建專用 branch／file 並固定 commit 讀回已驗證。本 repo 尚無 request JSON bridge。
- Function 是唯讀固定路由；metadata 僅 `fetched_at/source/environment`。fetched_at 是取資料時間，不是內容版本。
- 現有 row `version` 與 `content_revisions` 不在公開投影中，維持既有隱私／權限語義；不能順手把它們拿來當網站版本公開。

## 待資料模型確定的版本契約

推薦提供獨立的「公開行程內容版本」，讓 Chat 的受控修改結果、API 及頁面能引用同一版。
其涵蓋範圍需包含本次驗站所依賴的公開日程與餐饮／交通內容；不能只更新日期版本，卻無法識別餐廳或交通已變。
如何原子產生、涵蓋哪些依賴以及是獨立 revision 或公開內容摘要值，由六天模型規格定義。
不要求使用者手動算 hash，不拿 fetched_at、核實日期、Git commit 或備援檔 hash 混當資料版本。

## 請求／結果契約草案

路徑與欄位名稱待規格固定；以下是最小必要語義：

- 請求：唯一 request ID、目標行程／日期穩定 ID、預期公開內容版本、需要驗證的公開顯示值。
- CI 綁定：請求 commit、測試程式 commit、Actions run ID 分開記錄，使用受信任主線測試程式，只把請求分支視為資料輸入。
- 正式站觀察：固定正式目標 URL、實際 API／DOM 的公開內容版本、主活動／餐飲／交通欄位、即時或備援來源、手機錯誤與溢出狀態。
- 回報：request ID、預期與實際版本、通過／不符／仍舊版／使用備援／無法連線等結果、時間戳、差異摘要、截圖引用。
- 結果分支獨立於部署／請求觸發分支，避免結果回寫造成循環；回報檔的 commit 本身不證明正式站正在執行該版。
- 等待快取更新須有期限；逾時就說明觀察到的舊版本，不無限輪詢，也不把有 fallback 的畫面當最新修改通過。
- CI 失敗不回滾已成功的內容更新；Chat 需區分資料修改成功、驗站失敗及失敗原因。

## 驗收例子

使用者要求某天改成 Safari：Chat 受控更新並取得版本；CI 對該日期驗主活動與相應餐飲／交通，核對頁面版本與來源，再產出與 request ID 對應的 GitHub 報告。
只有網站能開、只有 workflow 綠燈，或只看到未關聯本次請求的截圖，都不足以證明此次修改已生效。

## 發布規則維護

請求格式、結果格式、版本語義與觸發路徑進內容／工程契約；Chat 完整指示保留使用入口，OpenCode 維護實作與驗收證據。
正式發布與 Chat 實際讀到新版分別記錄；目前未發布的新文件不能被當作 Chat 可用規則。
