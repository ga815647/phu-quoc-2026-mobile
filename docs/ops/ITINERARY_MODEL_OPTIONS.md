## 目標與已知限制

使用者只透過 Chat 改行程，網站讀取／導航。修改某日活動時餐飲、交通、可選尾段與備案需一致；一次修改可影響多日，但不碰已確認訂單。Neon 是唯一內容來源，GitHub JSON 只是投影。

現有卡片的 dining.place 是文字或集合，不是穩定店家 ID。food_pool 大多能經 notion_id 引用店家；vinwonders-inside 是 NULL 的合法園內餐飲例外，不能捏造店家 ID。現有 content_update 只有單列單欄交易，不能作跨日／跨關聯原子修改入口。

## 選項與推薦

| 選項 | 優點 | 代價 |
|---|---|---|
| 完整六天 JSON 單一內容列 | 單筆版本與原子更新簡單 | 局部修改容易重送無關資料，穩定關聯與約束較弱 |
| 全面正規化日／段／餐飲／交通／條件多表 | 強查詢與細粒度約束 | 對單次六天旅程較重，實作與維護範圍大 |
| **專用行程＋每日安排＋受控變更（推薦）** | 日期及既有內容 ID 明確；一次變更可原子處理受影響日，不需重送整份行程 | 需新增專用結構、驗證及受控入口，經正式規格審閱 |

推薦保留專用 itinerary 主檔及可獨立定位的每日安排；有序段落的實體表／JSONB 取捨在規格依查詢與完整性需求固定，不增加通用行程平台。Chat 只提交受影響日期的完整候選安排與理由，資料庫在一次交易驗證並套用；不是多次呼叫單欄更新再希望剛好一致。

## 一次行程變更的契約提案

1. 讀取目前行程版本與受影響日期，重用 cards.slug、food_place stable ID 或明確的 pool-only 例外。將方案預設建議與使用者明確選定餐廳分開。
2. Chat 整理有限的變更：日期／主活動指派、餐飲引用、交通段及備案。一般建議隨主活動換；使用者刻意指定且不合新路線的店家，先追問一次，不靜默刪除或保留不合理安排。
3. 受控入口接收 expected revision、唯一 request ID、受影響日期的候選安排及原因。鎖定行程、驗版本、日期／ID／條件及已確認預訂約束，整包成功或整包回滾。
4. 同 request ID 相同 payload 重送回原結果；同 ID 不同 payload 拒絕。記錄真實前後值；還原使用目前版本建立新紀錄，不刪稽核。
5. 返回此次內容變更的辨識，Chat 讀回稽核與公開行程，提交 CI 請求。API／畫面的公開內容辨識需涵蓋實際依賴的餐飲交通變更，不能只用行程日期計數器；內部 row version／audit 保持不公開。
6. CI 看同一公開投影与實際 DOM；報告 request ID、expected／observed content identity、即時或備援來源與差異。網頁驗收失敗不回滾已成功內容修改。

## 例子

將一個彈性日由 VinWonders 換成纜車：主活動／適用時段／去回交通／方案衍生餐飲一起換；An Thoi 成為可跳過尾段；不保留不相干的北島晚餐建議。已刻意指定的餐廳若不合路線，先追問一次；已確認預訂的變更不在此操作內。

## 三個已確認的行為邊界（2026-09-27）

- **旅途中可改範圍**：使用者同意新「每日安排」及其餐飲／交通指派在旅途中可經 Chat 受控修改；店家研究主表與已確認預訂沿用原限制，不因換日覆寫來源事實。新結構與入口尚待規格、實作及驗收，目前不能使用不存在的入口或繞過既有凍結。
- **明確餐廳選擇與新路線衝突**：一般預設自動跟隨；只有使用者刻意指定的店家不合路線才問一次，避免擅自抹掉原意。
- **約 21:00**：晚間活動結束目標，回住宿時間另外估列；不是要求 21:00 已回房，也不是不顧孩子狀態硬撐到該時刻。

## 現有證據不再重驗

Chat 正式唯讀與非正式分支受控寫入鏈已通過；新的批次行程入口另依需求實作及驗收。HTTP 由 CI 驗站承接，不要求 Chat 瀏覽器。這些能力證據不授權新 schema／public projection 直接部署。
