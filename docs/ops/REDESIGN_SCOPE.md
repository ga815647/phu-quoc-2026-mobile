## 1. 分工與唯一維護位置

| 對象 | 主要維護位置 | Chat 的責任 | OpenCode 的責任 | 網站的責任 |
|---|---|---|---|---|
| 旅遊研究、店家、行程卡、交通與公開預訂摘要 | Neon，依內容契約與穩定 ID | 查證、提出建議、執行使用者已要求且能力可用的白名單內容更新 | 接線、測試、匯出；Chat 通道受阻時依具體授權暫代內容維護 | 讀取公開投影，呈現來源、核實日期與備援狀態 |
| 私人每日索引、付款／取消、私人費用、現金與行李 | 既有私人 Notion 頁 | 授權範圍內最小更新、保留勾選並讀回 | 工程任務不搬移或公開私人內容 | 不複製私人準備功能與資料 |
| UI、生成器、樣式、互動與測試 | Git 程式原始碼 | 描述需求、提供驗收回饋 | 設計、實作、驗證與授權發布 | 提供旅途中執行介面 |
| 既有本機暫排／吃過狀態 | 使用者裝置 localStorage | 不宣稱可直接修改使用者手機狀態 | 保留舊資料；Chat 修改鏈路驗收後轉向網站唯讀行程 | 現有功能不回寫訂單、Neon 或 Notion；吃過等輕量狀態另行保留 |
| 角色、內容欄位與可修改範圍 | 本文件＋內容契約；入口為 AGENTS／Chat 指示 | 每次相關任務先讀現行契約 | 隨實作變更同步維護規則與證據 | 不把資料維護權限提供給公開按鈕 |

Chat／OpenCode 是責任分工，不是資料庫的技術角色名稱。工具具備寫入能力，不代表工程改版自動取得所有資料的修改授權。

## 2. 本轮已確認的產品決策

以下是已確認的設計方向，尚未代表已實作或已写入 Neon：

- 六天都有具體、可直接採用的預設安排；必要時可換日，暫排與已確認預訂分開。
- OnBird 保持既有已確認安排。三個彈性日預設採 VinWonders、纜車、Safari；海星保留五卡中的替換候選，不刪卡。三者具體日期與先後仍待完整估時安排。
- 不想自駕或張羅整日車輛，Grab 優先，既有業者接送照用。偏遠回程可靠性須有依據，不把 Grab 當保證。
- An Thoi 為纜車日順路加點，時間與狀態適合才去，不占獨立一天。
- 每餐有可直接採用的建議店家，以想吃、順路為原則；備選按需展開。早餐繞行、等車與下一段交通一起計時。
- 納入分段交通估時及緩衝。查得的時刻、估算區間與核實日期分開，不用預定到達時間減出發時間冒充實測車程。
- 以孩子為主；使用者已確認約 21:00 為晚間活動結束目標，回住宿時間另外估列。提早結束主活動可接低強度尾段，仍依孩子狀態調整，不硬撐。
- 一般預設餐廳隨新路線調整；只有使用者刻意指定的餐廳與新路線衝突時才追問一次，不靜默刪掉明確選擇。
- 使用者已確認新「每日安排」及其餐飲／交通指派在旅途中可經 Chat 受控修改；既有研究主表、已確認預訂仍沿用凍結／授權限制。這是新模型的行為範圍，不表示入口已存在或已授權直接執行 migration。
- 2026-09-27 改採 Chat 修改行程、網站閱讀與導航；日期或方案更動後餐飲交通跟隨的需求仍在，但不新增手機行程編輯器。通道與功能驗收前不直接移除既有操作，保留舊裝置狀態。

## 3. 目前允許執行與下一階段範圍

### 現階段：需求／邊界／設計

可直接進行唯讀事實查核、需求決策紀錄、術語表與角色／範圍文件維護。規格與實作計畫仍需完成使用者審閱。

2026-09-27 使用者已核准 `../superpowers/specs/2026-09-27-itinerary-chat-ci-design.md` 書面規格。已據此形成三份實作子計畫（資料／reader／CI），入口為 `../superpowers/plans/2026-09-27-itinerary-implementation.md`；目前待使用者審閱計畫。沿用已選定的 Subagent-driven 執行，工程候選驗收與正式內容／視覺／發布前置分別記錄。

### 設計與計畫確認後：工程實作

- 主責原始檔：`tools/build_site.py`、`tools/site.css`；有需要的新互動模組／公開資產，在計畫中列明路徑與責任。
- 修改相關 UI 測試與檢查，但保留五卡、餐飲清單、可觸控、無水平溢出與本機狀態持久化等既有語義。
- `index.html`、`data.html`、`card.html` 由生成器產生，不手改。候選輸出以明確 `--api-base/--out-dir` 隔離；正式輸出依既有 `--prod` 流程。
- JSON 是 Neon 公開投影的備援，不以手改 JSON 建立另一份正式內容來源。
- 更新內容契約、規則入口與驗收紀錄，狀態必須區分提案、已實作、本地驗證、已發布、Chat 端已驗證。

### 本輪工程範圍未包含的操作

正式內容批量覆寫、已確認訂單變更、資料庫 schema／權限／Function 寫入介面、登入或跨裝置同步、私人 Notion 結構重整及歷史資料清除，均不因 UI 改版而自動包含。若設計確有需要，先明列具體變更再確認範圍；既有已授權的日常內容更新仍按契約執行，不改成一律禁止 production。

## 4. 必須在規格中解決的資料歸屬

現有契約僅有三個彈性日的本機 slots，沒有六天公開預設行程的專用資料結構。因此「Chat 修改六天安排＋餐飲交通跟隨＋網站讀回」不能被標成現成能力，也不能偷偷硬編碼一份長期由工程維護的旅遊資料副本。

設計需逐項說明：公開預設日期／活動關係、餐廳穩定 ID、交通估時與來源、條件式備案如何使用現有 Neon 欄位；若需要新結構，列 migration、內容維護入口與授權需求，另經規格審閱。純顯示文字、排版與互動規則由程式維護。

私人 Notion 的每日索引與網站本機暫排各有既有用途，不做自動雙向同步。新公開預設不能取代或複製私人索引內容；若需要改變其責任分工，先明確取得使用者決定。

## 5. Subagent 分工

| 任務 | 可改範圍 | 交付／限制 |
|---|---|---|
| 事實與內容查核 | 唯讀資料／文件；指定研究報告 | 穩定 ID、來源、日期、未知事項；不順手寫正式資料 |
| 資訊架構與視覺 | 核准的規格、草圖／候選目錄 | 使用公開資料；不修改已確認預訂或擴大公開欄位 |
| 生成器／互動實作 | 計畫指定的原始碼與測試 | 保留資料契約、本機狀態與備援語義 |
| 規格／品質審查 | 預設唯讀 | 分別核對需求與程式品質、狀態保留、手機體驗 |
| 整合與發布 | 主代理統一處理 | 審查 diff、執行驗證、確認來源及發布狀態 |

每次派工帶入目標、允許修改路徑、資料寫入範圍（預設唯讀）、來源契約、驗收條件。共用檔案由單一寫入者負責；可獨立的查核／審查才平行。採 Superpowers 的設計確認 → writing-plans → subagent-driven-development；grilling 負責訪談，不再疊加另一套實作流程。

## 6. 發布與能力證據

- GitHub Pages 獨立預覽路徑目前是提案，尚未發布；需確認預覽部署範圍。正式首頁升版與預覽發布分開記錄。
- Chat GitHub／Notion、Neon 正式資料列讀取與指定測試分支受控更新鏈，依 `CHAT_ACCEPT.md` 的 2026-09-27 使用者提供證據通過；OpenCode 本輪另只核對 GitHub probe 產物，未代跑 connector。
- OpenCode 能操作 Neon，不代表 Chat 通道已恢復；網站 API 可讀，也不代表網站可以寫回。
- 本次 Chat 的 Neon 恢復有其自身回報證據；HTTP／畫面仍受該 Chat 環境限制。可由 OpenCode／CI 與手機驗 API／畫面，依同一變更版本關聯，不標成 Chat 親測，也不因此重開整包能力盤點。
- 2026-09-27 使用者選定 Chat 直接讀 GitHub 作為規則／程式／已發布驗收證據入口，不要求 Chat GET 正式網站。每次相關任務將 main 解析為單一 commit；最新旅遊內容仍由 Neon 讀寫，GitHub JSON 僅為帶日期的備援。網站 runtime／畫面由 OpenCode／CI 與手機按同一變更版本驗收；GitHub 文件或綠燈不能單獨代替畫面證據。
- 使用者其後已確認「Chat 修改 → CI 驗正式站 → GitHub 回報」納入設計：Chat 提交請求 JSON，CI 以瀏覽器核對該次內容，JSON／文字報告進專用結果分支、截圖進 artifact。既有測試可沿用，但 request bridge、公開內容版本與結果契約尚待實作；設計輸入見 `CHAT_CI_DESIGN.md`。
- 本地規則改動、Git 發布、ChatGPT Project settings 安裝、網站發布與內容維護能力各自記錄。文件尚未發布前，不宣稱 Chat 已取得新規則。

## 7. 維護方式

每個涉及資料來源、欄位、操作能力或責任歸屬的變更，由主代理在同一交付中更新本文件及內容契約的對照；AGENTS 與 Chat 指示保留入口，不複製整套規則。只改樣式不反覆要求使用者重貼 Chat 指示。

驗收記錄至少列：變更對象／穩定 ID、來源與核實日期、影響的資料→API→畫面→備援段落、實際通過證據、未完成項目。實作範圍新增時更新本文件及計畫，不以 subagent 的完成宣告代替核對。
